# 可见任务契约

本参考只在要创建、继续、跟踪或整合可见任务时读取。机器约束以 [路由策略](routing-policy.json)为唯一事实源；本文不是第二事实源，也不赋予工具、模型或创建权限。

## 授权与工具

先核对当前宿主的项目列举、创建、继续、状态或等待工具定义。工具存在不表示已获得授权，且当前工具更严格的要求优先。

- 创建任务必须有当前用户的显式创建授权，或可信项目规则中明确的持续工作包授权；泛泛的“开始实施”或“继续”不构成新建授权。
- 新建前从真实项目清单选择工程，核对 Git 属性、起点、文件主责和依赖；不硬编码项目 ID，不自动使用无项目任务。
- Git 默认使用工作树；用户明确选择保存项目直接工作时尊重该选择。非 Git 工程使用真实共享目录，所有可写文件集合必须互斥。
- 新工作树不保证包含未提交规则或未跟踪资源。首条请求须注明有效规则版本、真实工程、起点与基线，并提供必要的最小约束；缺失依赖显式处理，不自动复制凭据或完整历史。测试与构建生成目录也纳入文件主责。
- `clientThreadId` 只表示创建中，记录为 `pending`，不得作为正式 `threadId` 继续发送消息；返回不确定时先查找或对账，禁止盲目重复创建。
- 严格可见范围内不得以内部 subagent 替代。仅当某个必需只读角色落在可见范围内时，才要求宿主提供可核对的可见只读能力；大型/高风险的 `all_delegated` 路线会触发该门。机械或普通标准的可见实施不凭空要求审查沙箱。缺少已触发的能力时停止并报告。

## 请求、复用与跟踪

创建或继续前先查工作包：只有目标、工程、主责文件和上下文仍适用的任务才能复用；直接修复优先继续原任务。模型组合或其他执行请求被明确确认“未启动”时不消耗执行请求，但保留尝试记录；创建中、执行不确定或已经启动后失败的请求保留预算占位，直到能证明未执行。

模型按当前任务覆盖、角色模型覆盖、能力档模型的顺序解析；推理强度单独按当前任务覆盖、角色 reasoning 的顺序解析。可见任务为解析偏好时，机械类别对应 batch-worker 的 economy 档，标准和大型/高风险对应 implementer 的 balanced 档；这不是角色身份或沙箱的声明。宿主拒绝模型/推理组合时，记录拒绝并停止，不静默换模型或重试。新建任务省略字段时使用宿主或用户默认；继续既有任务省略字段时才表示沿用既有请求。两种省略都不能称为已降档或已启用轻量模型。若当前宿主要求显式指定模型，则档案偏好不能替代用户对具体模型的选择；没有该选择时先请求授权，不得省略字段后声称已使用轻量模型。工具没有回显运行配置时，只能记录“请求已提交，运行配置未确认”。

使用有界等待或状态快照，避免反复读完整历史；当前回合结束后没有持久监控机制时，不承诺持续监控。

## 工作包预算与集成

同一用户验收目标只有一个根工作包；拆出的子项继承 `root_work_package_id`，不能以拆分、重分类、换模型、换协调者、交接或直接修复重置计数。根包将内部 subagent 与可见任务合并计数：最多三个新执行上下文、六个执行请求，默认并发最多二、职责独立时最多三。继续、重试和会触发执行的澄清都计请求；纯读取、等待和不触发执行的澄清不计。

每一类的 strong 职责席位、strong 执行请求和单角色上限以策略为准。预留不是可自由使用的额度：标准任务只在有失败或未知证据时作 architect 诊断与必要澄清；大型/高风险按 architect 判断、final-reviewer 首审和一次修复后复审的有界次序执行。超限需要具体失败或未知、缩小目标和用户明确扩展；一般性“继续”不够。

子任务交付后先为 `awaiting_integration`。唯一协调者核对集成顺序、最终树和新鲜验证证据后才可标为 `completed`；两个工作树各自通过不等于集成通过。关闭或归档不自动释放仍在执行的文件主责。

## 记录

只有实际委派或跨会话持续工作才建立记录，并由唯一协调者维护。用户指定或确认位置后可从 [工作包模板](../assets/work-package-template.md)开始。记录不得进入安装 `state.json`、可移植档案或公开发布包，也不得包含凭据、完整聊天或原始日志。

需要交接时复用一份精简交接记录，保留有效规格、基线、在途任务、根预算和下一步。新协调者核对唯一主责与接管证据前，不派发、不写共享文件；不自动创建替代协调任务，不以交接清零预算。
