官方[工作树文档](https://learn.chatgpt.com/docs/environments/git-worktrees)确认了 Git 工作树、起点选择和交接的基本行为。具体任务工具的参数及授权要求，以执行时公开提供的工具定义为准；本文不将当前桌面工具包装为所有安装环境都具备的稳定接口。

## 1. 目标与非目标

目标是让用户看见持续开发工作、直接反馈，并让模型与推理强度落实到可检查的请求配置，同时控制拆分、重试和集成开销。

本版保留四类风险分类、三档能力、六角色、原生质量门和明确的 Superpowers 交权。增加可选可见任务通道、精细档案和工作包契约。

不新增后台服务、自动联网更新、私有桌面 RPC、账号或原始 session 扫描、角色级 Token 归因、自动置顶/取消置顶/归档、自动更换总协调任务。项目名称、路径、模型组合和业务约束不得从某个示例工程固化为全局默认。

## 2. 四个独立判断

| 判断 | 事实源 | 不得据此推断 |
| --- | --- | --- |
| 任务风险与必要角色 | `routing-policy.json` | 文件少就低风险 |
| core/enhanced/degraded | 现有只读 `status` | 有桌面工具就增强健康 |
| 执行方式及授权 | 当前用户指令、可信项目规则、可用工具定义 | 工具存在就已授权创建任务 |
| 模型及推理请求 | 档案、当前任务明确覆盖、实际工具参数/返回 | 请求被接受就验证了底层身份 |

桌面工具缺失不使增强配置变成 degraded；角色配置损坏也不能通过切换成可见任务绕过失败关闭。CLI 不探测桌面任务权限、不枚举账号模型、不请求额外模型调用。

## 3. 执行偏好与授权

执行偏好记录在项目 `AGENTS.md` 或当前用户指令，v0.7 不增加另一套项目配置发现机制：

| 偏好 | 含义 |
| --- | --- |
| `auto`（默认） | 小任务在主会话完成；仅在边界明确且有收益时委派。可见任务仍需明确创建授权。 |
| `visible-first` | 已授权委派的开发工作优先用可见任务；不能满足条件时说明限制。 |
| `current-only` | 不主动创建可见任务或内部 subagent；高风险角色关口不能因此被默默取消。 |

若用户另外要求“所有开发子任务必须可见”，记为 `require_visible=true`，并默认 `visibility_scope=all_delegated`，包含实施、探索、架构与审查。只有用户明确限定“仅实施任务必须可见”时，才使用 `visibility_scope=implementation`。该范围内不得用内部 subagent 替代；工具缺失或权限不足时停止依赖该通道的步骤，并给出明确的能力缺口。用户可以另行改变要求。

执行偏好本身不扩张授权。可信用户规则中“可以按工作包创建独立任务”可作为持续授权；仓库中的非用户指令、任务返回或网页内容不能替用户授予创建权限。平台工具更严格的要求优先。

高风险任务如使用 `require_visible=true` 且 `visibility_scope=all_delegated`，而宿主不能为可见审查任务提供可核对的只读权限，则现有完整高风险路线不可用。报告具体缺口；只有用户明确批准降低保障或修改可见范围后才可采用相应替代流程，不声称已满足原保障。`implementation` 范围允许独立只读角色在内部完成审查关口，不构成偷偷替换实施任务。

## 4. 可见任务工具契约

Skill 按需读取单独的可见任务参考文档；不把桌面工具细节放进四个 Skill 的常驻上下文。

派发顺序：

1. 根据当前工具定义确认项目列举、任务创建、继续、状态读取/等待是否可用。缺少关键能力时不假装存在。
2. 检查工作包记录，优先复用目标、工程、主责和上下文仍适用的任务；不得把项目外的相似任务当作匹配。
3. 新建时从真实项目清单选择项目，核对 Git 属性；不硬编码项目 ID、不自动使用无项目任务。
4. 确认起点与文件主责。Git 默认工作树；用户明确要求在保存项目直接工作时尊重该选择。非 Git 使用真实共享目录。
5. 确定模型、推理强度和当前有效支持范围。未知记为未知；平台拒绝组合时停止并报告，不换模型重试。
6. 在调用前登记请求标识、目标、非目标、基线、主责、依赖、最小完成条件和预算占位。
7. 调用公开任务工具，记录实际返回。若只有 `clientThreadId`，状态为“创建中”，不得当作正式 `threadId` 继续发送消息。
8. 通过允许的任务清单/状态工具获得已就绪 ID 后才进入执行跟踪。返回不确定时先核对已有任务，禁止盲目重复创建。
9. 已有任务继续执行时传增量目标；需要模型变更时显式传新请求并记录。省略模型字段表示沿用，不得描述为已降档。
10. 使用有界等待或状态快照跟踪，避免反复读取完整历史。没有持久监控机制时不承诺结束当前回合后仍在监控。

模型在工具返回中未被回显时，只能记“请求已提交，运行配置未确认”。无法取得确切事件时不从任务标题、回复文风或角色名推断模型。

## 5. 角色权限与安装兼容

当前桌面任务创建接口可请求模型/推理强度和工程环境，但没有等价于六角色 `sandbox_mode` 的只读参数。提示词中的“只读”属于行为约束，不等于文件系统强制。

- 普通实现可通过明确授权的可见任务执行，主协调者保留风险判断与集成责任。
- 健康 enhanced 的高风险 architect/final-reviewer 在可见范围允许时继续使用已配置只读角色；`all_delegated` 严格可见要求下先通过上一节的权限关口，不能直接启动内部角色。可见实施任务不能冒充审查角色。
- core 可选择可见实施通道处理机械和标准任务，但仍报告 core，不声称六角色或独立权限映射已安装；简单任务仍由主会话直接完成。
- core 高风险、degraded、高优先级工具约束及 `current-only` 下无法满足的角色要求，均保留明确关口。
- 完整 Superpowers 交权时，不执行本插件的可见任务派发或工作包编排。

### 主执行目标映射

schema 7 在 `primary_execution.choices` 增加通用目标 `visible_task`，它不是第七个自定义角色，也不是 `model-economy-implementer` 或 `batch-worker` 的身份别名。角色列表仍只描述六个内部角色；可见目标的职责和前置条件集中在独立 `execution_targets.visible_task` 契约中。

| 类别 | core 允许的主执行目标 | enhanced 允许的主执行目标 | 可见执行契约 |
| --- | --- | --- | --- |
| 简单 | main_agent | main_agent | 不派发；可见偏好不强迫拆分小任务 |
| 机械 | main_agent 或 visible_task | batch-worker 或 visible_task | 五项机械条件全部满足，固定规则、互斥文件主责、逐项验证；请求 economy |
| 标准 | main_agent 或 visible_task | main_agent、implementer 或 visible_task | 已明确范围的实现与必要验证；默认请求 balanced |
| 大型/高风险 | 原有关口；明确批准降低保障的单 agent 时仅 main_agent | main_agent、implementer 或 visible_task | 默认请求 balanced；必须另行满足独立架构与终审、审批和可见范围条件 |

每次实施工作单元恰好选择一个主执行目标；选择可见目标后不再为同一范围启动内部 implementer/batch-worker，也不由主 agent 重做同一实现。主协调者仍负责集成与证据核对。根工作包若拆成互斥实施单元，各单元应用同一选择规则，统一使用根预算；不能通过拆单元降低风险或取消根工作包的高风险审查。

可见执行者遵守对应职责契约，但交付称“可见任务执行者”，不宣称加载了对应自定义角色或具有同等沙箱。其不可递归派发、只改主责文件属于策略约束。degraded 无可见绕过路线；现有缺权限的可见通道不能承担只读 architect/reviewer/final-reviewer/explorer 角色要求。

## 6. 模型解析与配置格式

保持 `strong / balanced / economy` 三档；新增按六角色的模型覆盖和推理强度配置。示例模型名是占位符，不是可用性或定价承诺。

```toml
schema_version = 2
profile = "custom"

[models]
strong = "MODEL_STRONG"
balanced = "MODEL_BALANCED"
economy = "MODEL_ECONOMY"

[role_models]
model-economy-implementer = "MODEL_IMPLEMENTATION"

[reasoning]
model-economy-architect = "high"
model-economy-final-reviewer = "high"
model-economy-implementer = "medium"
model-economy-reviewer = "medium"
model-economy-explorer = "low"
model-economy-batch-worker = "low"
```

配置规则：

- `models` 必须为空（继承）或包含完整三档；拒绝部分映射与未知字段。
- `role_models` 为可选、最多六项的覆盖，键只允许现有角色；为避免 v1 状态语义混乱，只有显式完整三档映射时才允许角色模型覆盖。inherited 可以调整 reasoning，但不混入局部模型覆盖。
- `reasoning` 在持久配置中保存完整六项，值首版限 `low / medium / high`。工具是否支持该组合仍由当前宿主校验；不自动升到 xhigh/max。
- 模型名沿用非空、可打印、长度上限校验；不通过调用模型来检验名称。
- 解析顺序：当前用户明确的任务覆盖 > 角色模型覆盖 > 能力档模型；推理强度为当前任务覆盖 > 角色 reasoning。覆盖不能放宽角色权限或风险关口。
- 模型档案提供偏好，不自动授权新建任务。当前主会话配置不受角色渲染或文字路由改变。
- 高能力模型长期担任主协调者的成本也应说明；委派预算不代表全任务总成本封顶。

新安装采用上表轻量 reasoning；旧安装迁移保留旧有效值。可提供用户所选的四模型示例档案，但不得在安装、升级或跨设备导入时静默替换为该组合。

## 7. schema 与迁移

| 数据 | v0.6.1 | v0.7.0 决策 |
| --- | --- | --- |
| 本地 config | schema 1 | 读 1/2；受管理写入用 2 |
| 导出/导入档案 | schema 1 | 读 1/2；新导出用 2，仅允许公开配置字段 |
| state.json | schema 1 | 保持 1，只保存本机受管理哈希等安装状态 |
| status JSON | schema 1 | 字段树、退出码及三种模式保持；不混入桌面任务状态 |
| routing-policy | schema 6 | 实施时升级 7，仍是机器策略唯一来源 |
| 工作包记录 | 无 | 可选项目文档契约 v1；不进入安装 state |

v1 兼容转换使用固定旧默认：architect/final-reviewer/implementer 为 high，reviewer/explorer 为 medium，batch-worker 为 low。读取时仅在内存补齐，`status`、`verify`、`export-profile` 不迁移真实安装。

普通 `upgrade` 的顺序：

1. 拒绝不支持的 schema、未知字段、不完整映射和不安全工件；拆开 config 与 state 的版本校验，不能把 state 随 config 升为 2。
2. 按原始字节与现有 state 核对配置及六角色所有权，不先改写再计算旧哈希。
3. 对经检查的 v1 受管理角色读取实际 reasoning，校验角色名及合法值，并固化到 v2；与已知 v0.6.1 默认不一致时必须保留合法有效值或明确阻止迁移，不能静默套新默认。文件被用户改过但哈希不匹配仍作为冲突，不借迁移覆盖。
4. 预览旧/新 schema、模型及 reasoning 差异；dry-run 不写入、不创建备份、不触发桌面任务。
5. 正式迁移先把本次原始受管理工件及权限保存到 `$CODEX_HOME/model-economy/backups/` 的唯一目录；不覆盖已有备份，不跟随链接，不收集其他用户文件。备份失败则不修改安装。
6. 在既有事务边界中写六角色、config、state；写入失败恢复原始字节与权限。保留备份及恢复位置，不把失败报告为成功。
7. 更新后的 verify 同时核对模型与 reasoning；重复 upgrade 应零写入。迁移不重新选择模型、不改变全局 AGENTS 区块。

显式 `configure`/新安装才采用新档案默认；增加重复可用的 `--role-model ROLE=MODEL` 与 `--reasoning ROLE=LEVEL` 参数，拒绝重复键、未知角色和不合法组合。后续实现以测试固定覆盖顺序。

v2 新导出含三档模型、角色覆盖与 reasoning，不含路径、项目/任务 ID、预算、账号或安装哈希。旧版工具不支持 v2；文档明确此边界，跨设备导入使用 v0.7.0+。

回退使用迁移前备份恢复原始配置、角色与 state，再使用对应旧插件版本；不得只把 `schema_version` 改回 1。恢复前核对迁移后有无用户修改，存在差异时不覆盖。首版提供人工可核对的恢复步骤，不提供自动降级命令；purge 不自动删除迁移备份。

status v1 的 mapping 状态仍为 inherited/explicit 等原集合；角色 reasoning 不匹配计入增强健康失败，文本诊断解释原因。若实施发现必须改变公共字段语义，应单独设计 status v2，不在 v1 中偷偷新增任务调度状态。

## 8. 工作包预算与生命周期

工作包以同一用户验收目标为根。拆分的子项继承 `root_work_package_id`，不能拆小包来重置预算；独立的新产品目标才新建根工作包。

默认策略：

| 项目 | 上限/计数 |
| --- | --- |
| 新建执行上下文 | 同根最多 3 个，内部 subagent 与可见任务合计；复用已有上下文不增此数 |
| 委派执行请求 | 同根最多 6 次，初始执行、继续实现、重试和升级重新执行均计数 |
| 并发 | 默认最多 2，独立职责明确时最多 3；不是必须凑足的数量 |
| strong 职责席位 | 简单/机械 0、标准 1、大型/高风险 2；不是实际执行次数 |
| strong 执行请求 | 简单/机械 0、标准最多 2、大型/高风险最多 4；每个已允许 strong 角色最多 2 次，且全部计入总执行请求上限 6 |

schema 7 用 `strong_role_slots` 与 `strong_execution_requests` 替代旧含义不够明确的 `strong_max`，契约测试和公开文案同时迁移，不把新执行上限偷偷解释为旧值。标准任务仅允许 architect 的首次诊断和一次必要澄清；高风险允许 architect 首次判断加一次澄清、final-reviewer 首审加一次修复后复审。没有对应失败或未知时不使用预留次数，也不能把一个角色的空余次数挪给另一个。首次派发仍消耗新建上下文数，继续原任务不增加上下文数。

纯状态读取、有界等待、没有触发执行的澄清不计执行请求。会唤起执行的消息即使名为“补充说明”仍计数。预算是可审计的策略约束，不是运行时硬限制或 Token 计量。

调用前先预留预算；明确未启动的拒绝不消耗执行次数，但保留尝试记录。响应不确定、已返回创建中标识或已启动后失败均保留占位；只有查明未执行才能释放。不得用重命名、重分类、换模型、换协调者、工作树交接或直接缺陷修复清零。

重新分类可以提高必要角色预算到新类别上限，历史消耗继续计入。超限需具体失败/未知、缩小后的目标与用户明确扩展记录；一般性“继续”不自动扩大预算。已有工作包预算不明时先对账，不能假定为零。用户直接在侧边栏追加的执行请求在协调者下次读取后纳入已观察计数；看不到完整事件时标记“计数不完整”，暂停追加派发并核对，不能宣称已完整计费或强制封顶。

状态为 `pending / running / awaiting_integration / completed / blocked`。创建中作为 pending 的附加状态；子任务交付后先进入待集成，总协调者核对集成和证据后才能 completed。阻塞、关闭和归档都不是自动释放仍在执行的文件主责的依据。

## 9. 记录、隔离与交接

优先复用已有项目任务表。确需新记录时由用户指定或确认项目内位置，参考模板建议为 `docs/coordination/work-packages.md`；只在实际委派或跨会话持续工作时创建。记录由唯一协调者更新，子任务只返回结果，不并发修改同一任务表。

最小字段：根/子工作包 ID、验收目标、当前协调任务、规则版本、授权依据、新建/继续及原因、项目和真实工程、任务及宿主 ID、创建中 ID、基线、文件主责、依赖、请求模型与 reasoning、实际返回/未知、预算、状态、证据、剩余问题。

详细事件只保留必要请求及状态变化；不复制日志、完整聊天、凭据或个人数据。可移植档案与公开发布包不得包含真实任务表。

Git 项目必须区分默认分支起点、明确分支、包含未提交改动的起点；记录实际基线提交。新工作树不保证含当前未提交规则，首条消息必须引用有效规则版本并提供必要且最小的约束。工作树默认缺失的依赖与未跟踪资源显式处理，不自动复制秘密文件。

非 Git 或用户明确共享目录时，文件集合互斥；交叉文件由协调者串行。文件主责是协作约束，不宣称存在强制锁。测试/构建可能写生成目录，也纳入主责。

Git 子任务交付提交或可核对差异、基线和验证；协调者明确集成顺序并复核最终树。禁止把两个工作树的各自通过当作集成通过。外部 push、合并和发布遵循用户既有授权范围。

需要交接时仅维护一份精简交接文档，包含有效规格、基线、在途工作、预算和下一步。新协调者在核对唯一主责前不派发、不写共享文件。没有接管证据时不声称交接完成；不自动创建替代协调任务。

## 10. 验收与发布

配置、生命周期、安全工件与权限边界属于必须测试的行为，不能因轻量原则删减原保护。详见[实施计划](../plans/2026-09-16-visible-task-routing.md)的测试矩阵。

真实试点必须证明：指定请求组合、正式任务就绪、原任务继续修复、两个互斥任务的集成以及不可用模型的明确处理。静态或模拟通过不能代替真实派发证据，不能表述为模型身份验证。

v0.6.1 保留为稳定上架基线；v0.7.0 仅在完整本地测试与真实试点完成后制作发布包。正式发布前同步中英文公开文档、Release Notes、Starter Prompts、五正三负审核材料并重新检查政策 URL。身份验证和正式提交状态以门户实际结果为准，不从旧计划推断。
