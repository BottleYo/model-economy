# 工作原理

> 本文说明 v0.7.0 路由契约。真实可见任务试点经批准从本次发布门槛豁免，仍属未验证项。这些规则不是平台强制执行的调度器；旧版行为以 v0.6.1 标签为准。

Model Economy 是一套工作流策略，不会自动宣称模型质量或花费结果。策略先分类任务，再限制可以参与的角色。

## 安装模式

- **核心模式：**四个 Skill 不依赖本地六角色配置即可运行。简单任务由主 Agent 执行；机械和标准任务默认也由主 Agent 执行，明确获准且宿主支持时可选择可见任务实施。原生质量门不变，不声称拥有自定义角色或独立模型身份。
- **增强模式：**六个受管理角色文件、哈希、映射与模板版本全部健康后，才允许使用六角色路由。
- **降级状态：**部分缺失、冲突或过期的增强文件会失败关闭，绝不静默当作核心模式。

核心模式无法满足大型/高风险任务的独立架构师与终审员关口，因此必须报告限制，并让用户选择安装增强模式，或明确批准降低保障的单 Agent 路线。后者不得被报告为完整的 Model Economy 高风险流程。

## 分类顺序

分类采用 `first_match`，顺序如下：

1. **大型或高风险**：出现任一高风险边界、新架构或影响范围很广的改动。
2. **机械**：五项 economy 条件必须全部成立：输入和规则确定、操作可独立重试、没有敏感或高风险边界、每项都有自动检查、失败有明确上界。
3. **简单**：文件已知、没有开放判断、可直接验证，且不包含创意或行为变更。
4. **标准**：兜底类别。

## 增强模式能力关口

| 类别 | 角色与能力规则 | strong 职责席位 | strong 执行请求 |
| --- | --- | --- | --- |
| 大型或高风险 | 审批前 `architect` 完成只读决策；批准后选择主 Agent、`implementer` 或获准的可见实施任务；验证后 `final-reviewer` 完成独立终审 | 2 | 最多 4 |
| 机械 | 五项条件全部满足后，选择 `batch-worker` 或获准的可见任务，按 economy 职责逐项检查 | 0 | 0 |
| 简单 | 主 Agent 直接处理，不委派 | 0 | 0 |
| 标准 | 主 Agent、`implementer` 或获准的可见任务择一实施；其他角色按条件使用 | 1 | 最多 2 |

席位表示可参与的 strong 职责种类，不是调用次数。每个允许的 strong 角色最多执行两次：首次判断及有必要证据的一次澄清，或终审后的修复复审；没有具体未知或失败不使用预留次数，也不跨角色挪用。它们全部计入下文的总执行请求预算。这些都是策略级上限，不证明可用性或底层身份。

## 角色边界

- `architect` 和 `final-reviewer` 使用 `strong`，且只读；不得写计划、补丁或代码。
- `implementer` 使用 `balanced`，只能写入已批准范围内的实现、测试和验证。
- `reviewer` 使用 `balanced`，且只读。
- `explorer` 使用 `economy`，且只读；只收集最小事实，不产出设计或编辑。
- `batch-worker` 使用 `economy`，只可在符合条件的固定规则工作中写入，并逐项检查。

主 agent 始终保留分类、审批检查、写入协调、风险决策和最终验证责任。

大型/高风险任务需要额外事实时，`explorer` 负责只读事实收集；它仍占根工作包预算，不是自动追加的固定环节。

## 原生质量内核

Model Economy 自带四个按条件触发的质量门：意图门只在实质歧义、高风险决策或未批准架构边界存在时阻塞实施；计划门让简单任务直接执行、标准任务使用短计划、大型任务使用持久化计划；测试门按行为风险选择测试先行或替代检查；证据门要求完成前运行并核对新鲜验证。

这些门不是固定流水线。用户目标和验收已经明确时不重复设计审批；文档、纯格式和确定性配置不强制形式化 TDD；验证失败或无法运行时必须如实披露。

## 轻量工程能力

Model Economy 可以在不改变路由的前提下按需加载三个专项叶子 Skill：

| Skill | 触发场景 | 输出 |
| --- | --- | --- |
| `domain-context` | 领域用词、不变量或 ADR 对当前任务有直接影响 | 最小术语表、约束与文档冲突 |
| `module-design` | 需要检查模块边界、耦合或变更面 | 边界问题、接口取舍与最小改进 |
| `disposable-prototype` | 一个具体未知用小实验比继续讨论更便宜 | 隔离实验、观察结果与生产决策输入 |

叶子 Skill 的 `classification_effect` 为 `none`，`subagent_starts` 为 `0`。它们不拥有代理编排权，不创建额外计划或审查，不自行提交。原型不得使用任何真实账户，不得产生任何外部写入或破坏性副作用，也不得从认证文件、环境变量、钥匙串、token cache 或原始会话数据库取得凭据。正式代码仍按原任务类别经过风险匹配的审批、测试和验证。

## 单一编排权与 Superpowers

按指令优先级选择一套编排。Model Economy 默认是角色拓扑、能力档位、subagent 预算和完成门的唯一事实源。安装、启用或发现 Superpowers 不构成完整工作流授权。

只有用户在当前任务中明确要求“完整 Superpowers”或“Superpowers strict mode”时，Model Economy 才把本次编排权交给 Superpowers，并退化为模型与成本建议。单项测试先行、系统化调试或完成前验证请求不等于 strict 授权；交权状态不跨任务保存。

标准任务只有在文件位置、依赖或现有事实不明确时才允许 explorer；只有跨模块、关键逻辑、非显然回归风险或实质测试覆盖疑问出现时才允许 reviewer。两次实质失败或已有具体能力不匹配证据时，允许只读 architect 诊断；先记录证据和缩小的问题，不盲目重试。发现高风险后重新分类，但历史预算不清零。

## 可见任务通道

安装模式与执行通道是两件事：桌面任务工具可用不等于六角色增强健康。`visible_task` 是通用执行目标，不是第七个角色，也不冒充自定义角色身份。

- `auto` 按收益决定是否委派；`visible-first` 优先考虑可见任务；`current-only` 不主动委派。任何偏好都不自动授予创建权限。
- 新建需要用户明确创建请求，或用户确认的可信项目规则中的持续工作包创建授权；当前宿主工具更严格的授权要求仍优先，项目规则不能绕过它。先核对真实项目、起点、文件主责、模型及推理请求。Git 默认工作树，明确要求共享目录时尊重该选择；非 Git 使用真实共享目录。
- “所有开发子任务必须可见”默认覆盖所有委派（`all_delegated`）；只有用户明确限制为实施时才使用 `implementation`。不得用内部代理偷偷替代范围内的可见任务。
- 可见任务的“只读”提示不等于只读沙箱。必要只读角色无法满足时停止并报告；严格全部可见的高风险任务不能自动改走内部审查，也不能静默降低保障。
- 同一实施单元恰好选择一个主执行目标；直接修复优先继续原任务，换模型不等于换任务。模型或推理组合被拒绝时不静默替换；新建时省略参数使用宿主默认，继续时省略表示沿用，两者都不代表已降档。
- 只有创建中 ID 时不得当正式任务 ID 使用；响应不确定时先对账，不重复创建。模型未回显时只记录请求已提交，运行配置未确认，身份始终未验证。
- 子任务交付先进入待集成；核对最终树和验证后才完成。文件主责不是硬锁，两个工作树分别通过不等于集成通过。

规则细节按需读取 [可见任务契约](../../plugins/model-economy/skills/cost-aware-development/references/visible-tasks.md)。官方[工作树说明](https://learn.chatgpt.com/docs/environments/git-worktrees)用于解释隔离与起点；具体参数仍以当前工具定义为准。完整 Superpowers 模式下，Model Economy 不执行可见派发或工作包编排。

## 根工作包预算

同一验收目标下，内部代理与可见任务合计最多新建 3 个执行上下文、发起 6 次委派执行请求。默认最多 2 个并行，职责独立时最多 3 个，不要求凑满。继续、重试、模型升级后重新执行都计数；状态读取和未触发执行的澄清不计。

调用前预留预算，明确未启动的拒绝可释放；创建中、响应不明和启动后失败保留占位，查明后再处理。拆子包、换协调者或重分类不清零；用户直接在任务里续跑也纳入已观察记录。历史不完整时暂停追加并对账，超限需要用户明确扩展，一般性“继续”不扩充预算。

这是编排预算，不是总 Token 上限；主协调者自身也消耗额度。记录复用已有任务表，只在实际委派或跨会话持续工作时按确认位置创建，不复制完整聊天或凭据。

## 审批与验证

目标存在实质歧义、不同方案会显著改变结果、涉及高风险决策或未批准架构边界时，实施前必须获得可追溯审批。目标与验收明确、可复现缺陷、已批准设计内实施和确定性工作不重复审批。

声明完成前必须重新运行与变更相关的验证并检查结果。成本优化不应绕过必要审批、风险匹配测试、验证或安全检查。

reviewer 评估变更；final-reviewer 评估大型或高风险任务的残余交付风险；完成前验证核对新鲜证据。三者是不同证据层，不应重复执行完整代码审查。

## 委派前检查

委派前移除密钥、token、个人数据、生产数据、内部 URL 和无关路径，并明确非目标与验证命令。写入前声明文件集合（包括测试和构建输出），并行集合不得重叠；重叠工作由主 Agent 串行协调。子任务禁止递归委派，唯一协调者负责记录、预算与集成；归档或标记关闭不自动释放仍在执行的主责。

## 限制

- 可选的 CodexBar 摘要可以显示本地用量和估算成本，但不建立节省基线，也不进行角色归因。
- 当前 smoke 输出只能观察 Subagent 是否启动；角色和模型身份未验证。
- 适用时，项目指令可以覆盖全局路由。
